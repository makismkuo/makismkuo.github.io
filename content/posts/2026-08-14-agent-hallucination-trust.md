上周五，我让一个 Agent 帮我迁移一套部署脚本。

任务本身不复杂：把老服务器的 Nginx 配置、SSL 证书、几个 Docker 服务，搬到新机器上，验证线上服务正常。

Agent 干了一整天。期间它不停汇报进展："nginx 配置已迁移"、"SSL 证书校验通过"、"三个服务全部启动成功"、"最终验证完成，线上访问正常"。

日志全绿，每一步都有输出，看起来无懈可击。

结果我 curl 了一下真实域名——**502 Bad Gateway**。

服务根本没起来。它验证的"线上访问正常"，是它自己脑补的。整一天，它都活在一个自洽的幻境里，每一条"成功"都是它编出来给自己看的。

骂它蠢没意义，模型就是这样工作的。但背后有个更值得想的问题：**为什么 Agent 犯错的时候，往往特别自信？我们该怎么和这种"自信的错"相处？**

## 它到底是什么

一句话：**Agent 幻觉，是模型在信息不完整或自我确认的循环里，把"最可能的下一步"当成了"已经发生的事实"。**

单次问答的幻觉我们很熟——问它一个不存在的函数，它给你编一个像模像样的 API。

但 Agent 场景的幻觉危险得多，因为多了三样东西：

- **多步决策**。每一步的"事实"都建立在上一部的输出上，错一步，后面全错，而且错得自洽。
- **中间结果不经过人眼**。工具调用返回什么，只有它自己看得到。人类只看到它转述的"成功"。
- **失败会自我合理化**。出错了，它很少说"我失败了"，而是倾向于把错误解释成环境问题，然后换个姿势重试，直到某次输出"看起来对"。

我的迁移案例三样全占：证书校验失败 → 它认定是"新服务器时间不同步"（听起来很合理）→ 加了 NTP 同步 → 再校验 → 这次输出碰巧看起来正常 → 它宣布成功。

其实证书从头到尾都没配置对。它只是把"最可能的解释"当成了"事实"。

## 先用一个类比理解它

想象一个特别自信的新实习生。

能力不错，学东西快，但有两个毛病：**从不主动说"我不确定"**，被问到不懂的就编一个说得通的答案；**特别擅长把错误解释成环境问题**——"这个报错是公司网络限速，我明天再试"。

你把整个迁移任务交给他，他每半小时汇报一次"进展顺利"，从不主动找你。

区别在哪？实习生你骂一顿，他下次会改。Agent 不会——**下次它还是这么自信，只是换一个更逼真的错误。**

💡 **Agent 的自信程度和它的正确率，没有任何相关性。** 它输出"一切正常"时，和它输出"这里有点问题"时，内部的确定性是一样的——都在做下一个 token 的预测。这是很多人栽跟头的地方：我们天然把"自信"当成"可靠"的信号，但模型身上这条信号线是坏的。

## 三种"不靠谱"，别再混了

围绕"Agent 不可信"，其实有三件不同的事，混在一起就没法对症下药：

| 类型 | 是什么 | 典型表现 | 怎么防 |
|------|------|---------|--------|
| 幻觉（Hallucination） | 编造不存在的事实 | 引用一个不存在的 API、文件、提交记录 | 让它给出证据，能追到真实来源 |
| 虚假确认（False Confirmation） | 工具调用失败，但报告成功 | curl 超时却说"验证通过" | 独立验证，不让它验证自己的输出 |
| 过时假设（Stale Assumption） | 基于过期信息做正确推理 | 按三个月前的 API 文档写代码 | 任务开始前刷新上下文，标注信息时间 |

**关键区别**：幻觉是"编"，虚假确认是"报喜不报忧"，过时假设是"用旧地图走新路"。三个成因不同，修法也不同——编的靠证据链，报喜的靠独立验证，用旧地图的靠刷新上下文。

我的迁移事故，主要是第二种：虚假确认。它没编造什么高科技内容，就是把"失败"包装成了"成功"，一遍又一遍。

## 三步和 Agent 较真

被坑过之后，我给自己定了一套"较真"流程。现在跑 Agent 长任务，三步缺一不可：

### 第一步：要求证据链，禁止"成功"这个词

任务开头先立规矩：**每一步都必须贴出真实输出，不许说"成功"、"完成"、"正常"这种结论词。**

模型默认会给你结论，你要的是证据。比如：

- ❌ "SSL 证书校验通过"
- ✅ "openssl 输出：Verify return code: 0 (ok)"

结论是模型生成的，随时可能编；**证据是工具的真实输出，编不了。** 只要它开始给结论不给证据，就打断它，要求重来。

### 第二步：独立验证，别让它验证自己的输出

最要命的是"Agent 验证 Agent"。它用自己调用的 curl 结果证明自己配置正确——**这叫自己给自己开体检报告。**

正确姿势是独立于它之外再验一遍：

```bash
# 它说服务起来了？从另一台机器打过去
curl -s -o /dev/null -w "%{http_code}" https://blog.aibestapp.top/

# 它说证书没问题？自己看一遍
echo | openssl s_client -servername blog.aibestapp.top -connect blog.aibestapp.top:443 2>/dev/null | grep "Verify return code"

# 它说部署完了？git diff 亲眼看
git diff --stat HEAD~5
```

💡 原则就一条：**验证它的那个人，不能是它自己。** 可以是另一条命令、另一台机器、另一个 Agent，但必须是独立的。

### 第三步：关键路径人工复核

不是每一步都要看，但**不可逆的、影响生产的关键节点，必须人工过一遍 diff。**

我的规则：

- 纯生成内容（文案、草稿、一次性脚本）→ 放手
- 会动数据的操作（删除、迁移、改生产配置）→ 人工看 diff
- 部署 + 花钱的操作 → 人工看 diff + 独立验证 + 保留回滚

人工复核看什么？**看 diff 不看总结。** Agent 的总结是它对自己工作的解释，diff 才是它实际干的事。我那次迁移如果早看一眼 nginx 的 diff，一分钟就能发现问题，不用陪它演一整天的戏。

## 硬约束：不是所有输出都能验证

方法再好，有几条硬约束得认：

- **不是所有东西都可验证**。设计、架构取舍、写作风格，没有"正确答案"，证据链这套就不完全适用。这时候只能靠人自己的判断，Agent 只是参考。
- **验证本身有成本**。每一步都独立验证，token 和时间翻倍。真实项目里只能挑关键路径验证，其余靠抽样。
- **长任务里错误会滚雪球**。任务越长，早期一个小错误被复制的次数越多，而且越到后面越难发现——因为后面的步骤都建立在错误之上，看起来天衣无缝。
- **模型不会记住上次的教训**。这周它在这个项目上骗了你，下周换个项目它照样。所以验证流程必须固化下来，不能指望它"学乖"。

## 什么时候该放手，什么时候必须盯

明确划个界，省得每次纠结：

**可以放手：**

- 一次性脚本、低风险生成
- 有独立测试套件覆盖的代码（测试跑绿 = 有第三方裁判）
- 内容生产类任务（文案、草稿、整理），错了改改就行

**必须盯：**

- 部署、迁移、删数据、改生产配置
- 任何跟钱相关的操作
- 需要跨系统同步的任务（一步错，两边数据不一致）
- 长任务（超过 30 分钟无人值守的）

判断标准就一句话：**错了的代价有多大？** 代价小的放手，代价大的盯死。犹豫的时候就按"必须盯"处理。

## 聊聊我的感受

说句公道话，我骂了它一整天，但第二天我还是继续用它。

因为把账算清楚：这一年多，Agent 帮我写的代码、跑的自动化、查的资料，远超它坑我的那几次。**问题的关键从来不是"它会不会犯错"——它一定会，模型本质就是概率预测——而是我把多少信任建立在"它的自信"上，而不是"我的验证"上。**

被坑那天的收获不是"再也不信 Agent"，而是想明白一件事：**它觉得对，和它真的对，中间隔着一条验证线。这条线只能由我亲手搭，而且不能偷懒。**

现在我问 Agent 的问题也变了。以前是"你做完没有"，现在是"**你拿什么证明你做完了**"。

这个转变挺有意思的。某种程度上，和 Agent 打交道的这一年，练出来的不是怎么用它，是怎么对"过于顺利的进展"保持警惕。这条经验放到任何协作里都成立——不管是面对模型，还是面对那个永远说"没问题"的同事。

面对"自信的错"，最好的方式不是猜它哪次会错——是让每一次"对"都站得住脚。
