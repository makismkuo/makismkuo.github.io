## 先给结论

**自建服务多了以后，最怕的不是服务挂了，是挂了没人知道。**

Uptime Kuma 是一个开源的网站监控工具：一条 `docker run` 拉起来，网页里点几下配置好要盯的服务，宕机 30 秒内就能收到 Telegram 通知，还自带一个可以分享出去的状态页。**免费、可控、不吵不闹。**

💡 一句话心得：**监控的价值不是"知道它挂了"，是在用户发现之前知道它挂了。**

---

## 背景：服务多了，宕机没人知道

我现在的"基础设施"长这样：

- 博客双域名（GitHub Pages + 香港服务器 Nginx 反代）
- Umami 统计、sub2api 中转、Tailscale 组网
- 服务器上跑着的一堆 Docker 容器

服务一多，一个问题就冒出来了：**这些服务到底活没活着，我根本不知道。**

上次写发布流水线的时候提过一个事——blog.aibestapp.top 的 443 端口被云防火墙过滤，国内经常超时。那次是读者打不开了、我才在验证脚本里发现。要是没有验证脚本，可能几天都没人发现。

网站是这样，服务器上的服务更是这样。白天盯着没事，半夜崩了，第二天早上用户来问"你的站挂了你知道吗"，那感觉真的不行。

所以我要的其实很简单：

1. 服务挂了，尽快通知我（最好是 Telegram 推到手机上）
2. 有一个公开的状态页，别人问我"你的站是不是挂了"时，直接甩链接
3. 自己掌控数据，不要为了一个监控再注册一个 SaaS

---

## 技术选型：为什么是 Uptime Kuma

选型的时候我对比了几个方案：

| 方案 | 免费额度 | 通知 | 状态页 | 数据在自己手里 |
|------|---------|------|--------|---------------|
| UptimeRobot | 50 个监控 / 5 分钟间隔 | 有 | 有限 | 否 |
| Grafana + Prometheus | 无限制 | 有 | 很强 | 是 |
| 商业监控（监控宝等） | 少 | 有 | 有 | 否 |
| **Uptime Kuma** | **无限制** | **有** | **有** | **是** |

**UptimeRobot** 其实够用，免费 50 个监控点，注册就能用。但 5 分钟的检测间隔意味着：服务挂了，最坏 5 分钟后才知道。而且数据都在人家那边，哪天想换监控、想导出历史，麻烦。

**Grafana + Prometheus** 是好东西，但那是给"正经系统"用的。我只需要知道"网站通不通、端口通不通"，为了这个上一套 Prometheus + 各种 Exporter，纯属杀鸡用牛刀，维护成本直接翻倍。

**Uptime Kuma** 刚好卡在中间：

- Docker 一条命令，数据存在本机 SQLite 里，备份就是拷一个文件
- 检测间隔可以短到 20 秒，还能配"重试 N 次才报警"，不怕网络抖动
- 通知渠道一堆：Telegram、钉钉、邮件、webhook、企业微信……国内国外都覆盖
- 自带状态页，勾选几个监控项就能生成一个公开页面
- 支持 HTTP(S)、TCP、ping、DNS、关键字检测，还有**心跳监控**（这个后面细说）

如果你也是"自建了几个服务、又不想上全家桶"的状态，它几乎是标准答案。

## 部署：Docker 一条命令 + Nginx 反代

### 第一步：拉起来

```bash
docker run -d --restart=always \
  --name uptime-kuma \
  -p 3001:3001 \
  -v uptime-kuma-data:/app/data \
  louislam/uptime-kuma:1
```

就这一条。跑起来后浏览器打开 `http://服务器IP:3001`，第一次进去设置管理员账号，完事。

关键点是 `-v uptime-kuma-data:/app/data`——Kuma 的所有配置和数据都存在这个目录下的 SQLite 文件里。**不挂载这个卷，容器一删，你的所有监控配置全部消失。** 后面踩坑里细说。

### 第二步：Nginx 反代 + HTTPS

Kuma 自己有用户名密码，但我不想记一个 `IP:3001` 的地址，也不想裸跑 HTTP。给它套一层反代：

```nginx
server {
    listen 443 ssl;
    server_name status.example.com;

    location / {
        proxy_pass http://127.0.0.1:3001;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

证书用 certbot 签一张，HTTPS 就齐了。SSL 证书这种操作我之前在《配一台个人服务器需要几步》里写过，流程一样，不重复了。

💡 **如果你只有一台机器，甚至可以不开反代**，直接用 IP + 端口 + 强密码。反代多一层，就多一个故障点——我自己的原则是：能少一层就少一层。

## 踩坑记录：五个真实事故

### 坑一：页面一直转圈，状态不刷新

部署完反代，网页能打开，但监控状态一直不更新，转圈转到天荒地老。

查了半天，原因：**Uptime Kuma 用 WebSocket 把状态实时推给前端**，我的 Nginx 配置里没放行 Upgrade 头，WebSocket 连不上，页面就拿不到实时状态。

修复就是上面配置里的三行：

```nginx
proxy_http_version 1.1;
proxy_set_header Upgrade $http_upgrade;
proxy_set_header Connection "upgrade";
```

💡 **凡是用 WebSocket 的应用套反代（还有 VSCode Server、Jupyter 这些），都要记得这三行。**

### 坑二：告警风暴，Telegram 被刷屏

配好监控和 Telegram 通知的当晚，凌晨三点，手机开始疯狂震动。

原因：服务器网络抖动，十几个监控项几乎同时"失败"，每个都触发了一次通知。一晚上收了上百条告警。

修复：每个监控项都设置**重试次数**——检测失败 N 次（比如 3 次）才真的算宕机、才发通知。网络抖一下就过去了，不会误报。

💡 **告警通知要"慢半拍"：宁可晚 30 秒知道，也不要凌晨三点被刷屏吵醒。** 同理，恢复通知（Up 通知）我直接关了，只留宕机通知。

### 坑三：Docker 里的 ping 监控全军覆没

我给家里那台机器配了个 ping 监控，结果从第一天起就一直是红色的 Down，但那台机器明明活着。

原因：**Docker 容器默认没有 NET_RAW 权限，发不了 ICMP 包。** ping 类监控在容器里天然不好使。

解法两个：

- 跑容器时加 `--cap-add=NET_RAW`（或直接 `--network host`）
- 更省事：**别用 ping，改用 TCP 监控端口**，效果一样，还更贴近真实服务状态

我现在基本都是 HTTP/TCP 监控，ping 只用在个别没法用端口的场景。

### 坑四：监控了自己的反代域名，天天误报

前面说过 blog.aibestapp.top 有 443 超时问题（疑似腾讯云防火墙过滤）。我一开始给这个域名也配了监控，结果它天天报 Down，但实际上 GitHub Pages 那边是好的——只是国内链路连不上这个反代而已。

后来我把监控项调整成：

- **主链路**（makismkuo.github.io）单独监控，这个最重要
- **反代域名**的监控改成更长超时 + 更多重试，或者干脆不监控

💡 **监控也要分主次：别让一个本来就不稳定的增强链路，天天制造噪音。** 这跟发布流水线的原则一样——主链路通了就算在线，增强链路是加分项。

### 坑五：差点把整个监控配置删了

有次想升级 Kuma 镜像，手一滑执行了 `docker rm`，才发现我当初没挂卷。还好是在测试环境，重新配一遍也就十分钟。

教训就一条：**`/app/data` 这个卷必须挂，而且要定期备份。** Kuma 的整个状态（监控项、通知配置、状态页）全在里面的 SQLite 文件里，备份就是 `docker cp` 拷出来一个文件的事。

## 进阶：心跳监控，给定时任务上个保险

这是我最喜欢的功能，也是它和其他监控工具最大的区别。

上个月写了篇《AI Agent 定时任务自动化》，里面那些每天定时跑的任务（文章发布、数据抓取、RSS 同步），其实有一个共同的问题：**任务"应该"每天跑，但没人知道它到底跑没跑。** 跑挂了、跑一半卡住，日志里躺着，没人看就等于没发生。

Uptime Kuma 的心跳监控（Heartbeat）就是干这个的：

1. 新建一个监控，类型选 **Heartbeat**，它会生成一个带 token 的 URL
2. 在定时任务脚本最后加一行 curl 命令，任务跑完就"打点"一次：

```bash
# 任务跑完后发心跳
curl -fsS -m 10 --retry 5 \
  -o /dev/null \
  "https://status.example.com/api/push/<你的token>?status=up&msg=OK"
```

3. Kuma 里设置"超过 40 秒没收到心跳就算 Down"

效果：**任务正常跑，一切安静；任务没跑，几分钟内 Telegram 就响了。** 比看日志靠谱一百倍，因为它把"有没有发生"这件事变成了自动通知。

💡 我现在所有 cron 任务（包括每天写博客的发布脚本）都加了这么一行。**定时任务没有反馈，就等于没做。**

## 效果与建议

现在我的状态页挂在服务器上，公开链接随时可以甩给朋友："你自己看，是 GitHub Pages 挂了还是你网络的问题。"

Telegram 告警到现在真正触发过两次：一次是香港服务器被重启后 Docker 容器没自启（现在都加 `--restart=always` 了），一次就是上面说的反代误报。**次数不多，但每次都是"用户发现之前"就知道的。**

回看这一路，几条实在的建议：

**要做的：**
- 监控项设置重试次数，别让网络抖动制造告警风暴
- Docker 必须挂 `/app/data` 卷，定期备份
- 定时任务加心跳，把"跑没跑"变成自动通知
- 监控主链路，别监控不可达的增强链路

**不要做的：**
- 别用 ping 监控 Docker 里的服务（改用 TCP/HTTP）
- 别关掉恢复通知就完事——先关 Up 通知、留 Down 通知就够了
- 别为了监控上一整套 Grafana + Prometheus，先问自己到底需要知道什么

监控这个东西，装了以后你几乎感觉不到它的存在——而这恰恰是它最好的状态。**真正的价值不在于它发了多少告警，在于那些本该发生的告警，在你不知道的时候替你守住了。**
