2024 年 11 月，Anthropic 开源了 MCP，当天整个 AI 圈都沸腾了。人人都在说这是"AI 的 USB-C 接口"，是让模型长出手脚的关键一步。

到了 2026 年，风向完全变了。你刷技术社区，隔三差五就能看到类似的标题："MCP 是个失败的设计"、"MCP 快死了"、"为什么我不用 MCP"。

同一个东西，两年时间从神坛跌到谷底，也是挺戏剧的。

唱衰的有道理吗？有一点。但我这一年多一直在用它，跑过不少项目，想聊聊真实感受——**它到底解决了什么，又没解决什么。**

## 它到底是什么

一句话：**MCP（Model Context Protocol）是一套让 AI 模型调用外部工具、读取外部数据的标准化协议。**

模型本身不会用 GitHub，不会查数据库，不会读你服务器上的文件。MCP 干的事就是：定一套统一的接口，让"模型"和"外部能力"通过这个接口对话。

核心就三样东西：

- **Tools（工具）** — 模型能调用的函数，比如"搜索代码""查天气""创建 Issue"
- **Resources（资源）** — 模型能读取的数据，比如一份文档、一个数据库表
- **Prompts（提示词模板）** — 预置好的对话模板

传输方式两种：**stdio**（本地进程间通信，靠标准输入输出）和 **HTTP**（远程服务，走网络）。

底层是 JSON-RPC 2.0，就是"我说一句、你说一句"的请求响应模型。技术上没有魔法，甚至可以说有点朴素。

## 先用一个类比理解它

想想打印机行业。

在 USB 出现之前，每个打印机厂商都有自己的接口协议。你买个佳能打印机，得装佳能驱动；换惠普，得卸了重装。软件要支持打印机，得给每家厂商写一遍适配代码。

USB 出现后，一切统一了：接口是标准的，驱动是通用的，插上就能用。

💡 **MCP 之于 AI 工具，就像 USB 之于外设。** 以前模型要调 10 个工具，就要为每个工具写一套私有适配；现在只要大家遵守 MCP 规范，一套代码通吃。

这个类比能解释 MCP 为什么火：**它解决的痛点是真实且普遍的。** 每个做 AI 应用的人，都在为"连接外部世界"这件事重复造轮子。MCP 至少让轮子统一了尺寸。

## MCP vs 函数调用 vs ACP，别再混了

围绕"让 AI 干活"，市面上有几套东西，经常被混为一谈：

| 方案 | 本质 | 解决什么 | 谁主导 |
|------|------|---------|--------|
| 原生函数调用 | 模型 API 自带的能力，把函数 schema 塞进提示词 | 单次调用内执行一个函数 | 各模型厂商 |
| MCP | 标准化的工具发现+调用协议 | 跨模型、跨厂商统一接工具 | Linux 基金会（Anthropic 发起） |
| ACP | 让 Agent 之间互联的协议 | 客户端连接任意 Agent | Google |

**关键区别**：函数调用是"模型 API 的一部分"，MCP 是"模型和工具之间的一层协议"。用函数调用，你换模型就得重写适配；用 MCP，模型和工具都遵守同一套协议，两边解耦。

ACP 则更高一层——它不解决"模型调工具"，解决的是"你的 Agent 怎么接别的 Agent"。层次不一样，别放一起比。

## 三步接一个 MCP 服务

理论讲完，直接上手。以 Claude Code 为例，接一个文件系统工具：

### 第一步：装一个 MCP 服务器

```bash
# 用 npx 直接跑官方文件系统服务器
npx -y @modelcontextprotocol/server-filesystem /path/to/your/dir
```

跑起来后它会监听 stdio，等待客户端调用。就这么简单，一个服务器就是一个"给 AI 用的 API 服务"。

### 第二步：注册到你的客户端

```bash
claude mcp add filesystem -- npx -y @modelcontextprotocol/server-filesystem /path/to/your/dir
claude mcp list   # 查看已注册的服务器
```

也可以改配置文件（`~/.claude.json` 或项目级 `.mcp.json`），把服务器列表写进去，团队共享。

### 第三步：让模型用起来

```bash
claude
# 在对话里直接说：
# "用 filesystem 工具，列出 /path/to/your/dir 下的所有文件"
```

模型会自己发现可用的工具，按需调用。你不需要写任何胶水代码。

💡 **如果你想在网页应用里远程接 MCP**，就部署一个走 HTTP 的 MCP 服务器，把 URL 配给支持 MCP 的客户端即可。原理一样，只是传输层从 stdio 换成了 HTTP。

## 硬约束：MCP 不是万能的

用了一年多，必须说它的真实缺点，有几个硬约束：

- **无状态是最大的坑**。每次工具调用都是独立的，服务器不记得上一次调用。做多步操作（比如"登录→查数据→写入"），得靠客户端在上下文里带着状态跑，token 烧得飞快。
- **流式输出支持差**。MCP 的工具调用是"等结果全部返回"的模型，不适合流式生成场景。生成长内容时体验很割裂。
- **上下文膨胀**。工具列表、schema、历史结果全往上下文里塞。MCP 服务器接多了，一次对话的 token 消耗肉眼可见地涨。
- **工具调用的可靠性**。模型可能传错参数、可能幻觉出不存在的工具、可能调用失败后无限重试。协议本身不保证正确性，只保证"能连上"。
- **生态还很碎片**。官方 SDK 更新频繁，版本之间有不兼容；社区服务器质量参差，很多没人维护。

实打实说，这些限制不是吹毛求疵，是用过的人都会撞上的墙。

## 什么时候该用、什么时候不该用

**值得用：**
- 你的 AI 应用需要接多个外部工具，且未来可能换模型
- 你想用现成的社区 MCP 生态，不想自己写适配
- 团队多人协作，希望工具配置标准化
- 本地/私有工具需要安全可控地暴露给 AI

**别硬上：**
- 只调一两个自家 API，且模型不会换——直接函数调用更省事
- 对延迟和成本极其敏感的场景——MCP 的封装有额外开销
- 需要长链路、多步骤、有状态的任务——协议本身不适合，得自己兜底
- 追求极致稳定性的生产系统——生态还年轻，慎用

一句话总结我的判断：**MCP 是"标准化的下限"，不是"智能的上限"。** 它负责把工具接入这件事做统一，但任务能不能干成，还是看你的 Agent 设计。

## 聊聊我的感受

说实话，这两年关于 MCP 的争论，我一开始也挺摇摆。

早期它确实惊艳——第一次看到模型自己发现工具、自己调用、自己处理结果，那种"AI 真的有手了"的感觉，是真实的震撼。后来用多了，撞上无状态、上下文膨胀这些墙，又觉得"就这？"

但时间长了我想明白一件事：**一个协议被骂得最凶的时候，往往是它最普及的时候。** MCP 被吐槽，恰恰是因为它已经铺开到了几乎每个 AI 工具的默认配置里——大家不再讨论"要不要用"，而是"它哪里不够好"。这就是标准该有的样子。

它当然不是终点。流式、状态管理、认证体系，这些都在演进，Google 的 ACP 也在逼它往前走。但作为"把 AI 接进真实世界"的第一块通用拼图，它已经完成了自己的历史任务。

以后大概率不会有人再高呼"MCP 改变世界"，但它会像 HTTP、像 USB 一样，安静地躺在每一层技术栈里，没人注意，也没人离开它。

觉得这篇有用的话，随手点个 ⭐ 或者分享给正在折腾 Agent 的朋友，就是对我最大的支持。
