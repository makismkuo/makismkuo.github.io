如果当前 AI 编码助手是一个「超级个体」，那当你有两个、三个，甚至更多的时候会发生什么？

这不是科幻。我现在的日常工作流程里，有两个 AI Agent 同时在跑：Hermes Agent 负责调度和规划，Codex CLI 负责具体编码。它们的协作方式，比我预想中更有意思。

## 一个问题带来的想法

几个月前我遇到一个场景：我需要同时维护博客、写代码、部署服务、检查服务器状态。一个 Agent 做不过来——它刚写到一半代码，又要切换到服务器环境看日志，上下文塞满了不相干的信息。

这时候我的第一反应不是「找一个更强的 Agent」，而是「为什么不找两个 Agent 分工？」

一个做规划和协调，一个专门写代码。互不干扰，各司其职。

## 什么是 Agent 跨工具协作

简单说，就是一个 Agent（主控 Agent）有能力把任务委派给另一个 Agent（执行 Agent），然后等结果回来再继续。

这和人类团队的协作很像：

- **项目经理**→ 拆任务、派活、验收、协调
- **开发**→ 专注写代码，不管部署环境

在 AI Agent 的世界里，实现这种协作的关键协议叫 **ACP（Agent Communication Protocol）**。

## ACP 是什么

ACP 是 Agent 之间通信的标准协议。它定义了一套消息格式和传输方式，让不同厂商、不同工具的 Agent 能互相理解、互相调用。

打个比方：ACP 对 Agent 来说，就像 HTTP 对 Web 服务一样。你不需要知道对方用什么语言写的，只要双方都遵守协议，就能通信。

目前支持 ACP 的主流工具有：

- **Hermes Agent**（Nous Research）— 原生支持作为主控 Agent
- **Codex CLI**（OpenAI）— 支持 ACP 子进程模式
- **Claude Code**（Anthropic）— 支持 ACP 模式

💡 一个关键点：ACP 不是让两个 Agent「聊天」，而是让一个 Agent 把任务发给另一个，等结果返回。这是调用，不是对话。

## 实战：Hermes 调度 Codex

我的配置是这样工作的：

### 架构

```
你（人） → Hermes Agent（规划/决策/调度）
                    ↓
            delegate_task()
                    ↓
          Codex CLI（编码执行）
```

Hermes 收到你的需求后，会把编码任务拆出来，通过 `delegate_task` 工具发给 Codex。Codex 在自己的独立环境里完成编码，把结果摘要返回，Hermes 再继续处理后续工作。

### 实际效果

拿一个典型的「写文章并部署」流程举例：

1. 我告诉 Hermes：「今天写一篇关于 ACP 的文章，写完部署」
2. Hermes 先检查仓库状态、确认主题、列出大纲
3. 如果需要代码示例，Hermes 把「写一个 ACP 通信示例代码」的任务发给 Codex
4. Codex 独立完成代码编写，返回代码文件和摘要
5. Hermes 把代码嵌入文章，完成全文，push 部署

两个 Agent 各自只处理自己擅长的事，上下文不互相污染。

### 为什么不是单 Agent 解决一切

一个很大的 Agent 确实能处理所有事，但有两个实际问题：

**第一，上下文窗口是有限的。** 写完文章又要切到终端查日志，之前写了一半的代码片段还挂在上下文里，Agent 容易跑偏。

**第二，工具集不通用。** 编码 Agent 装了编译器和包管理器，调度 Agent 装了浏览器和网络搜索。混在一起，反而让工具选择变慢。

## 配置细节

如果你也想试试这种模式，需要的条件其实不多：

### 基本要求

1. **主控 Agent**：Hermes Agent（或其他支持 ACP 的 Agent 框架）
2. **执行 Agent**：Codex CLI（`npm install -g @openai/codex`），或其他 ACP 兼容工具
3. **配置**：在 Hermes 的 `config.yaml` 里启用 delegation：

```yaml
delegation:
  max_concurrent_children: 3
  max_spawn_depth: 1
```

然后就可以在 Hermes 里直接调用 `delegate_task` 了。

### 实际心得

跑了一段时间后，我总结了几条经验：

**1. 任务描述要自包含。**
子 Agent 没有你的对话历史。给它的 context 里要把文件路径、错误信息、约束条件全部写清楚。写得好，子 Agent 一次性完成；写得模糊，来回沟通的成本比自己做还高。

**2. 用摘要代替完整输出。**
子 Agent 返回的是摘要，不是完整的终端输出。这设计是对的——中间工具调用的结果没必要全塞进主 Agent 的上下文。但你得确保摘要包含了关键信息（状态码、文件路径、输出结果）。

**3. 并行是最大的甜头。**
支持同时跑 3 个子 Agent。搜索资料、写代码、生成图片可以同时进行。这在单 Agent 模式里是不可能的。

**4. 快任务不值得委派。**
如果只是查一个文件内容，或者跑一条命令，直接在终端里做就行。委派有初始化成本，适合 5 分钟以上的独立任务。

## 硬约束

不是所有任务都适合这种模式。几个实际遇到的限制：

- **子 Agent 不能问用户问题** — 遇到需要确认的地方只能自己决定，或者报错回来。所以不适合需要交互决策的任务。
- **没有持久化** — 如果你的主会话关闭了，还在跑的子 Agent 也跟着丢了。长任务建议用 Cron 而不是委派。
- **嵌套深度受限** — 目前只支持一级委派（主 Agent → 子 Agent），不支持子 Agent 再委派。这其实是个好的安全限制，防止 Agent 无限递归。

## 什么时候该用、什么时候不该用

**适合委派的任务：**

- 独立编码任务（实现一个功能、写一个测试）
- 调研/搜索合成（查资料 + 整理成报告）
- 代码审查（看完整项目然后给反馈）
- 并行任务（多个独立模块同时开发）

**不适合委派的任务：**

- 简单操作（改一行配置、查一个文件）
- 需要用户实时确认的任务
- 依赖主会话上下文才能理解的任务
- 几秒钟就能做完的事

## 聊聊我的感受

说实话，刚开始跑这套的时候，我觉得有点多此一举。一个 Agent 干活不是挺好的？何必再搭一套调度层。

但真正用了一周之后，感受变了。

最明显的变化是 **出错率降低了**。以前一个 Agent 什么都干，经常在切换上下文的时候漏掉关键信息——部署脚本写到一半，突然问我要不要继续写文章。现在流程清晰了：Hermes 管规划和验证，Codex 管编码，各管各的。

另一个意外的收获是 **心态上的变化**。知道自己有「团队」之后，开始真正用项目管理的思维来拆任务。以前是「帮我把这个做了」，现在是「这个功能分三步：先搭骨架，再写逻辑，最后写测试——分别委派出去」。这种思维方式一旦形成，效率反而上来了。

当然也有不爽的地方：子 Agent 返回的结果有时候过于简略，需要再追问。偶尔遇到网络波动，委派任务会超时。但这些都在可以接受的范围内。

ACP 协议本身还很新，生态也在快速迭代。但至少在我这个场景里，它已经从一个实验性功能变成了日常基础设施。

如果你也在用多个 AI 工具，不妨试试让它们协作而不是各自为战。两个 Agent 加在一起，不是 1+1=2，而是把各自最擅长的部分发挥到极致。

——Seb
