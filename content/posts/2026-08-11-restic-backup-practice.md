## 先给结论

**监控解决的是"挂了知道"，备份解决的是"挂了之后数据还在"。两件事，缺一不可。**

上一篇文章写 Uptime Kuma 的时候我说过一句：监控的价值不是"知道它挂了"，是在用户发现之前知道它挂了。但监控有个天花板——**它只能告诉你服务死了，救不回数据。** 真正让数据在灾难里活下来的，是备份。

我的方案最后落在 restic 上：单二进制、加密、去重、增量快照，本机 Mac 和服务器各一套，每天定时跑，备份完打个心跳给 Uptime Kuma。跑了两周，中间恢复演练过一次，把几个坑都踩明白了。

💡 一句话心得：**备份做得好不好，标准只有一个——灾难来了，你能不能真的恢复出来。** 其余都是过程。

## 背景：我是怎么意识到备份是个问题的

先说我现在的数据摊子：

- **Mac 本机**：博客仓库、一堆开源项目、Hermes 的配置和记忆、照片（这个走 iCloud，先不管）
- **香港服务器**：Nginx 反代配置、Uptime Kuma 的 SQLite 数据、Umami 统计库、sub2api 配置、一堆 Docker 卷

平时不觉得，但把清单列出来就发现：**这里面每一样，丢了都补不回来。** 博客文章丢了可以重写（痛苦但能活），Uptime Kuma 的监控配置丢了要重新配（十分钟），但 Umami 两年的访问统计数据、sub2api 的密钥配置、本地项目里没推上 GitHub 的代码——这些是真·唯一副本。

真正让我下定决心的是上个月一件事：服务器被机房重启，Docker 没自启，我远程上去一顿操作，**手一滑差点 `rm -rf` 了挂载目录**。虽然最后没事，但那几秒钟的冷汗是真实的。我在想：如果刚才真删了，我能恢复吗？

答案是不能。因为**我根本没有备份**。

那一刻我意识到一个扎心的事实：我写了这么多篇"自建"的文章，教别人搭这个搭那个，但自己的数据一直是裸奔的。这就像你装修房子装了一堆智能家居，却把门锁忘了。

## 技术选型：为什么是 restic

备份方案我认真对比了一圈，先说结论：**个人自建场景，restic 几乎是标准答案。**

| 方案 | 增量 | 去重 | 加密 | 版本历史 | 跨平台 | 备注 |
|------|------|------|------|---------|--------|------|
| rsync | 有 | 无 | 无 | 无 | 好 | 误删会同步误删 |
| tar + 定时 | 无 | 无 | 可选 | 手动 | 好 | 全量越来越大 |
| Time Machine | 有 | 有 | 可选 | 有 | 仅 Mac | 管不了服务器 |
| borg | 有 | 有 | 有 | 有 | 一般 | Python 依赖较重 |
| **restic** | **有** | **有** | **有** | **有** | **好** | **单二进制，哪都能跑** |

逐个说下我为什么淘汰了前面几个：

**rsync** 是我最早在用的。它的思路是"镜像"：本地什么样，远端就什么样。好处是简单，坏处是**没有历史版本**——本地误删一个文件，rsync 会把远端那份也删掉，等于同步了灾难。而且 rsync 不加密，往远端传就是裸奔。

**tar 定时全量** 的问题是体积。全量备份一次几个 GB，存几天磁盘就爆了。而且恢复的时候要从最新那份里翻，中间版本的差异想找回？没有。

**Time Machine** 其实是好东西，但它只管 Mac 本机，管不了我服务器上那堆 Docker 卷。我需要的是一个 Mac 和 Linux 都能跑的方案。

**borg** 和 restic 功能上非常接近，都做加密去重增量。我纠结过一阵，最后选 restic 的原因很实际：**restic 是单个静态二进制，下载就能跑，没有 Python 环境和依赖版本的问题**，在服务器上部署省心太多。而且 restic 对 S3、SFTP、本地磁盘、各种对象存储的支持都很顺，后端选择自由。

💡 如果你只有一台 Mac、没有服务器，Time Machine + 外置盘其实够用。**方案好坏取决于你的数据分布，不要为了上工具而上工具。**

## 部署：三台"机器"各就各位

我的备份拓扑长这样：

```
Mac 本机  ──restic backup──▶  服务器 /backup/restic-mac（加密仓库）
服务器    ──restic backup──▶  本机外置盘 /Volumes/Backup/restic-server（加密仓库）

两个仓库互相异地，任何一台机器没了，另一台都有对方的副本。
```

思路很朴素：**本机和服务器互备，谁也不依赖谁。** 服务器挂了，Mac 上有它的备份；Mac 挂了（或者丢了），服务器上有它的备份。家里要是进贼把 Mac 和服务器都端了……那属于极端情况，先不管。

### 第一步：装 restic

Mac 上：

```bash
brew install restic
```

服务器上更简单，直接下官方二进制：

```bash
curl -L -o /usr/local/bin/restic https://github.com/restic/restic/releases/latest/download/restic_linux_amd64.bz2
# 解压后 chmod +x，放到 PATH 里
```

就一个文件，没有任何依赖。这就是我选它的原因之一。

### 第二步：初始化仓库

每个备份目标都是一个"仓库"（repository），初始化一次：

```bash
# Mac 上：往服务器建仓库
restic init --repo sftp:user@server:/backup/restic-mac

# 服务器上：往我的外置盘建仓库
restic init --repo /Volumes/Backup/restic-server
```

初始化的时候会要求设**仓库密码**，这个密码就是仓库的加密密钥。**丢了它，整个仓库就是一堆无法解密的废数据**——后面踩坑专门讲。

### 第三步：写备份脚本

备份不能靠手点，要定时。我在 Mac 上写了个脚本 `~/bin/backup-mac.sh`：

```bash
#!/bin/bash
export RESTIC_PASSWORD=$(pass show backup/restic-mac)   # 密码从 pass 里取，不写死在脚本
export RESTIC_REPOSITORY=sftp:user@server:/backup/restic-mac

restic backup ~/workspace ~/Documents \
  --exclude '*.DS_Store' \
  --exclude '**/node_modules' \
  --exclude '**/.venv' \
  --exclude '**/target' \
  --exclude '**/.git' \
  --tag mac-daily

# 清理策略：只留最近 7 天每日、4 周每周、6 个月每月
restic forget --keep-daily 7 --keep-weekly 4 --keep-monthly 6 --prune

# 备份完打个心跳，Uptime Kuma 没收到就报警
curl -fsS -m 10 -o /dev/null \
  "https://status.example.com/api/push/<token>?status=up&msg=backup-ok"
```

两个细节值得展开：

**exclude 规则要狠。** `node_modules`、`.venv`、`target` 这些目录，一个项目动辄几百 MB，全是可再生垃圾，不排除的话仓库体积直接爆炸。`.git` 目录也是——仓库本身已经有远端 git 历史了，本地再备份一份纯属浪费空间。

**forget + prune 是黄金搭档。** restic 的 `forget` 只是把快照标记为删除，`--prune` 才真正释放空间。不跑 prune，被"删掉"的快照数据还占着磁盘。我一开始就忘了这茬，仓库越来越大，后面详细讲。

### 第四步：上定时器

Mac 上用 launchd（`crontab` 在 macOS 上也能用，但 launchd 更正规），服务器上用 systemd timer。核心就一条：**每天固定时间跑，且失败要能发现。**

launchd 的 plist 写起来啰嗦，我直接说 cron 版本，效果一样：

```cron
0 2 * * * /Users/makismkuo/bin/backup-mac.sh >> /tmp/backup-mac.log 2>&1
```

凌晨两点跑，因为那个点我肯定在睡觉，磁盘和带宽都是空闲的。

## 踩坑记录：四个差点让备份白做的坑

### 坑一：仓库密码差点弄丢

第一次 `restic init` 的时候，我随手设了个密码，想着"反正知道就行"。一周后我想在另一台机器上挂载仓库看快照，**怎么都想不起来密码是啥了。**

restic 仓库是加密的，**没有密码恢复机制，没有找回通道**。密码丢了，仓库里的所有备份全部作废，跟没备份一样。

修复：把密码写进 `pass`（密码管理器），脚本里通过 `$(pass show ...)` 读取，**密码不出现在任何明文文件里**。另外在密码管理器里记了一条恢复说明，万一 pass 本身出问题，还有个兜底。

💡 **备份的密码管理，和备份本身一样重要。** 建议：密码入密码管理器 + 纸面抄一份放抽屉，双保险。

### 坑二：忘了 prune，磁盘被快照撑爆

跑了大概一周，我看了眼服务器磁盘，发现 `/backup` 涨得飞快。查了下，是 `forget` 之后没加 `--prune`。

restic 的去重机制决定了它的快照管理方式：**快照只是索引，底层数据块是共享的。** `forget` 删掉快照后，那些块还在仓库里躺着，只有 `--prune` 会把没人引用的块真正删掉。

不加 prune 的后果：你以为"只留 7 天每日"，实际磁盘上的数据块是**从第一次备份到现在的所有版本**，一点没少。

修复：脚本里 `forget` 和 `--prune` 一起用，并且定期 `restic check` 验证仓库完整性。

### 坑三：备份成功没反馈，跑没跑不知道

这是最隐蔽的坑：**定时任务没有反馈，就等于没做。** 我在上一篇文章里写过这个观点（Uptime Kuma 的心跳监控就是干这个的），结果自己差点又犯。

第一版脚本只写了 `restic backup`，cron 日志落在 `/tmp` 里，**没人看。** 备份跑挂三天，我浑然不觉——直到某天我手动跑了一次，发现报错：SFTP 连接失败（服务器 SSH 密钥轮换过，旧密钥失效了）。

修复：脚本末尾加心跳 curl（就是上面脚本里那行），Uptime Kuma 40 分钟收不到心跳就 Telegram 报警。现在备份失败，我在手机上几分钟内就知道。

💡 血的教训：**任何自动化任务，第一件事不是让它跑，是让它"跑没跑"这件事可见。** 心跳、日志、通知，至少选一个。

### 坑四：恢复演练，发现 exclude 规则把重要目录误杀了

这个坑最有价值。搭好备份两周后，我做了一次完整的**恢复演练**——这是备份体系里最容易被跳过、也最重要的一步。

我在测试目录里执行：

```bash
restic restore latest --target /tmp/restore-test
```

结果傻眼了：**我的 `~/workspace` 里有个子项目 `scripts`，里面躺着一些没推上 GitHub 的脚本，恢复出来是空的。**

排查发现：那个项目里有个叫 `target` 的目录（Java 构建产物），我的 exclude 规则是 `**/target`，**它把项目根目录也叫 `target` 的那个文件夹整个排除了**——包括里面那个 `scripts` 子目录里的所有文件。

glob 匹配的坑：`**/target` 会匹配任何层级的 `target`，包括"恰好叫这个名字的顶层目录"。修复：exclude 规则改成 `**/target/**`（只排除 target 目录内部），顶层目录名单独检查。

💡 **备份配置了 ≠ 备份有效。** 唯一能证明备份有效的方式，就是真正恢复一次，检查文件内容对不对。我建议每季度做一次恢复演练，把"备份"从心理安慰变成真家伙。

## 效果与总结

现在跑了两周，说下实际状态：

- **Mac 本机**：每天凌晨 2 点备份到服务器，仓库现在约 4.2 GB（原始数据估计 15 GB+，去重加压缩省了一大半）
- **服务器**：每天备份到外置盘，约 1.8 GB，包含所有 Docker 卷配置和数据库
- **Uptime Kuma**：两个心跳监控，40 分钟无心跳即 Telegram 报警，目前没误报过
- **恢复演练**：做过一次完整 restore，除了坑四那个问题，其余文件逐字节校验一致

回看这一路，几条实在的建议：

**要做的：**
- 本机和服务器互备，异地副本才是真备份
- 仓库密码进密码管理器，再留一份纸面兜底
- exclude 规则要狠，`node_modules` 这种可再生垃圾一律排除
- `forget` 和 `--prune` 成对出现，定期 `restic check`
- 备份任务加心跳，失败要能自动通知你
- **至少每季度做一次恢复演练**

**不要做的：**
- 别把备份和同步混为一谈（rsync 不是备份，它没有历史版本）
- 别让密码只存在于脑子里，restic 没有找回通道
- 别用 `**/xxx` 这种宽松规则，先想清楚它会匹配到什么
- 别配置完就再也不看，备份日志和告警要真的被读到

最后说点感受。备份这件事，做完之后你**几乎感觉不到它的存在**——没有新功能可以炫耀，没有界面可以截图，它只是每天凌晨默默地跑一遍，然后在心跳里打个勾。

但这恰恰是我觉得它最像"基础设施"的地方。监控让你在服务挂掉的时候第一时间知道，备份让你在知道之后**还能睡得着觉**。前者是反应速度，后者是兜底能力。

真正的安全感不是"我知道我不会出事"，是"我知道万一出事，我有一整套预案"。对个人开发者来说，这套预案里最基础的一块，就是把备份这件事做得足够无感、足够可靠。
